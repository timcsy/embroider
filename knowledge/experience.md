## 教訓

<!--
  每個重要的教訓加一個小節。

  一律要有：實際發生 · 教訓 · 來源。

  開頭二選一，看哪個貼：
    - 「理論說」　　— 預期和實際之間有落差
    - 「怎麼撞到的」— 程序型教訓，沒有那個落差（「我這樣做了，而它救了我」）。
    　　　　　　　　 硬套「理論說」會逼出一個編造的錯誤預期，
    　　　　　　　　 那比格式不一致更糟。

  可選，而通常值得那個位置：
    - 「不適用的時候」— 邊界。一條沒有邊界的教訓會被過度套用，
      　結果是每換一個處境就重寫一次，而不是把它磨利一次。
    - 「相關」— 指向同族教訓的橫向連結。
      　一條教訓屬於哪一族，往往比那條教訓本身更有用。

  來源是最先掉的那條腿，尤其在你開始改寫這個格式之後。
  掉了它，結論還在，而產生它的那次場合沒了——你再也重建不回當時的思路。

  教訓要寫成「判準」，不是「做法」。做法（「把綁定層與算繪分離就能測」）
  會隨技術棧過期；判準（「一個會改變被測對象的量測器，量到的不是被測對象」）
  才跨處境。一條教訓完成的標誌，是它改掉了某個判準的寫法，
  不是它被寫下來了。

  別人常記下的教訓（看看有沒有戳中你踩過的）：
    1. 動手前先 print 定位，別急著用推理找 bug
    2. 大重構時，讓編譯器／型別檢查當「待改清單」
    3. 效能多半來自資料模型，不是微優化
    4.「錯 → 懂 → 修」勝過「想到完美再動手」
    5. 別跳過 TDD——「之後再補測試」通常 = debug 三倍久

### 自寫編碼器配自寫解碼器，錯誤會互相抵銷

- **理論說**：往返測試全綠就代表輸出檔正確。
- **實際發生**：pyembroidery 讀回時指出「跳針到起點後原地再下一針」被丟掉，並順藤摸瓜找到固定針在輪廓開頭有極短線段時退化成原地。
- **解決方式**：加獨立實作的讀回與逐點比對（`scripts/verify.sh`），先寫失敗測試再修。
- **教訓**：驗證者與被驗證者出自同一假設，驗到的是一致性不是正確性；至少一個檢查必須來自獨立來源。
- **不適用的時候**：沒有獨立實作可用時（例如 B70 實機本身是唯一的裁判）。
- **來源**：[格式不猜-全部輸出](history/格式不猜-全部輸出.md)、[沒有實機時怎麼把產品做完](episodes/2026-10-17-沒有實機時怎麼把產品做完.md)。

### 跨邊界的資料要在邊界上驗證，不要相信它的型別

- **理論說**：型別對、單元測試過，傳給 Web Worker 就沒問題。
- **實際發生**：Svelte `$state` 的代理物件無法結構化複製，只有真瀏覽器的端對端測試抓得到，同一類錯誤出現兩次。
- **教訓**：只在假環境裡測過的邊界等於沒測；邊界必須在會真正失敗的環境驗證。
- **來源**：2026-10-17 開發對話（Playwright 發現）。

### 使用者看得到的數字也要有測試

- **實際發生**：提示寫「放大到 17.2 公分」實際是 1.7 公分（0.1mm 單位換算錯），單元測試全過，看截圖才發現。
- **教訓**：內部量對不代表呈現給人的量對；顯示層的數字要有斷言。
- **來源**：2026-10-17 開發對話。

### 沒有實機資料時，假設要有名字、單位、集中一處

- **實際發生**：最小字高、筆畫寬、安全邊距等全是猜的。
- **教訓**：猜的值若散落各處，等實測回來就沒有人知道該改哪裡；標明是假設並集中，校正才是改一處。
- **來源**：[格式不猜-全部輸出](history/格式不猜-全部輸出.md)（`Settings` 在 `crates/stitch-gen/src/design.rs`）。

### 用乾淨的合成圖測，會漏掉真實圖片才有的問題

- **理論說**：圖片轉換用色塊分明的合成圖測過（色塊、圓、線），行為正確就代表好用。
- **實際發生**：使用者試用說「很難看」。換成有輪廓線、反鋸齒、JPEG 雜訊的卡通圖後，才看到花瓣之間的深色輪廓整條消失、邊緣有像素階梯、邊緣過渡色被繡成一圈米白邊。這些都是合成圖不會出現的。
- **解決方式**：造一張接近真實的測試圖（反鋸齒＋JPEG 壓縮），逐項先寫失敗測試：深色細線加粗而非刪除、平滑半徑跟著像素大小、顏色數建議不被面積門檻或雜訊誤導、近似的顏色合併、淺色過渡色併入背景。
- **教訓**：測試資料的來源若跟被測程式的假設相同（乾淨的色塊），測到的是假設不是產品；至少要有一組來自使用者真實素材的樣本。
- **來源**：2026-10-18 使用者試用回饋；測試在 `crates/stitch-image/tests/`。現場：[感恩節插畫逼出的圖片品質迭代](episodes/2026-10-19-感恩節插畫逼出的圖片品質迭代.md)。

### 換了做法，原本的代理指標就不再代表同一件事

- **理論說**：用「標題範圍內的針數」就能檢查標題文字有沒有被保留。
- **實際發生**：改成細長筆畫走緞面後，同樣完整的字針數從 5245 掉到 1785，測試轉紅，但畫面上的字反而清楚多了。緞面本來就比填充省針。
- **解決方式**：改量「1mm 方格中有針經過的格數」，量的是覆蓋範圍，與用哪種針法無關。
- **教訓**：指標若跟實作手法綁在一起，換手法時失敗的是指標不是產品；先確認它量的是結果，不是做法的副產品。
- **來源**：2026-10-18 圖片細長筆畫改走緞面；測試在 `crates/stitch-image/tests/pipeline.rs`。現場：[感恩節插畫逼出的圖片品質迭代](episodes/2026-10-19-感恩節插畫逼出的圖片品質迭代.md)。

### 自動更新對「記憶體裡的狀態」是破壞，不是方便

- **理論說**：PWA 用自動更新，使用者永遠用最新版，很省事。
- **實際發生**：使用者第一次選圖片後畫面自己跳回打字。原因是新版本的離線程式一啟用，頁面就被強制重新整理，選好的圖與設定都只在記憶體裡，全部消失。每次我重新建置，開著的分頁就會碰到一次。
- **解決方式**：改成不自動更新，新版等使用者下次重新打開才接手；加了測試守著設定不能再自動重新整理。
- **教訓**：任何會在使用者操作中途自行重新載入頁面的機制，都要先問「頁面裡有沒有尚未存下的東西」；有的話，更新時機必須交給使用者，而不是程式。
- **來源**：2026-10-18 使用者回報；`web/vite.config.ts`、`web/tests/deploy.test.ts`。現場：[感恩節插畫逼出的圖片品質迭代](episodes/2026-10-19-感恩節插畫逼出的圖片品質迭代.md)。

### 回報「做了」之前，要對著程式確認那一行真的改了

- **理論說**：改動是我自己寫的，記得做過什麼，回報不會錯。
- **實際發生**：一輪回報裡寫「字不再被加胖」，實際上程式裡那一行沒有動；到下一輪才發現，而且改了之後才暴露出另一個規則（最小筆畫）會把設計擋下來。另一次為了還原一行實驗，用 `git checkout` 還原整個檔案，把還沒 commit 的幾十行修改一併丟掉。
- **解決方式**：重做遺失的修改；之後實驗性還原前先 commit，回報前用 grep 或 diff 對照確認。
- **教訓**：口頭回報是記憶的產物，不是程式的產物；任何「已完成」都要附上能被驗證的證據（測試、diff），不能只靠印象。
- **來源**：2026-10-18 本人在圖片轉換迭代中的兩次失誤。現場：[感恩節插畫逼出的圖片品質迭代](episodes/2026-10-19-感恩節插畫逼出的圖片品質迭代.md)。

### 迭代式的幾何運算，每一輪都要把結果簡化，否則複雜度會滾雪球

- **理論說**：輪廓填充就是一圈圈把形狀往內縮，每圈偏移是便宜的運算，圈數也有限。
- **實際發生**：單元測試用乾淨的圓形，毫秒內完成；接上實際管線後，邊緣是像素階梯平滑出來的鋸齒，每偏移一圈凹角就多一堆小弧，頂點數越滾越大，一張簡單的圖從 0.2 秒變成跑了十幾分鐘，而且是在整套測試卡住不動時才發現。
- **解決方式**：每圈偏移後簡化輪廓（0.1mm 容許誤差）；補一個用鋸齒邊緣的測試並加上時間上限，確認拿掉簡化時測試會卡住。
- **教訓**：測資要有真實資料才有的「髒」（鋸齒、頂點多），而且凡是把上一步輸出當下一步輸入的迴圈，都要問一次「輸出的複雜度會不會每輪變大」。
- **來源**：2026-10-19 輪廓填充；`crates/stitch-gen/tests/contour.rs`。現場：[感恩節插畫逼出的圖片品質迭代](episodes/2026-10-19-感恩節插畫逼出的圖片品質迭代.md)。

### 讓元素取得鍵盤焦點，會悄悄把頁面捲走

- **理論說**：畫布一被碰到就 `focus()`，方向鍵才有作用，這是無害的小事。
- **實際發生**：雙指縮放的端對端測試算出多出 45 度的旋轉。追下去才發現：第一根手指落下時 `focus()` 讓瀏覽器把畫布捲進畫面，頁面移了 62 像素，第二根手指的座標就是在不同的捲動位置下算的，兩點連線因此歪了。真手機上這同樣會讓頁面在手指一碰就跳。
- **解決方式**：`focus({ preventScroll: true })`，並用真正的觸控事件（CDP）寫成端對端測試守住。
- **教訓**：互動中要「持續比較」的座標（兩指、拖移）必須在同一個座標系內取得；任何會改變座標系的副作用（捲動、縮放、重排）都要先排除。
- **來源**：2026-10-19 編輯器雙指縮放；`web/src/components/EditorCanvas.svelte`、`web/tests/e2e/editor-flow.spec.ts`。

### 同一個版面的決定只能有一個來源，不要各處各自量

- **理論說**：畫布自己看「我這一欄有多寬」就能決定要不要放大；頁面另外用視窗寬度決定要不要左右並排，兩邊的判斷看起來會一致。
- **實際發生**：平板直放（800 像素寬）時，頁面是上下排列，畫布卻因為「這一欄超過 700 像素」而放大到快一整個螢幕高，把下面所有工具與按鈕蓋住，端對端測試連「加文字」都點不到。電腦版另外被使用者直接說「超難用」：整頁要捲 2800 像素、畫布小、存檔鈕飄在中間。
- **解決方式**：由頁面決定一次版面模式（寬或窄），以參數傳給畫布；電腦版改成整頁不捲動，上面一條工具列，畫布與工具區各自捲動。
- **教訓**：影響版面的條件只在一個地方判斷，其他元件接收結果；自己量自己的寬度，在版面切換的邊界上一定會和頁面的決定不一致。
- **來源**：2026-10-19 使用者回報電腦版難用；`web/src/routes/EditorPage.svelte`（`wide`）、`web/src/components/EditorCanvas.svelte`（`fill`）、`web/tests/e2e/editor-flow.spec.ts`（電腦版、四種視窗）。

### 互動的回饋要「先動、再算準」：不加等待，並用舊結果即時變形

- **理論說**：預覽算得夠快就好；改動後等 120 毫秒再算（防抖）可以省下拖動中途的重複計算。
- **實際發生**：使用者說改畫布時要等一下才更新，尤其是改圖的大小。量測：每次改動約 160 毫秒才看到變化（120 毫秒是自己加的等待），圖片物件每次縮放都要重新鋪針；手機比開發機慢好幾倍。拖動時畫面上只有外框在動，針跡在手放開後才跳過去。
- **解決方式**：三層：①不加任何等待，沒有在算就立刻開始，正在算時只留最新一份（`scheduler.ts`），內容沒變（只是選了別的東西）就不重算；②核心另外回傳每個物件各自的針跡，畫布在拖動、縮放、旋轉時直接把舊針跡平移、旋轉、放大縮小到手指的位置，畫面立刻跟著動；③算超過一下子才出現細細的進度條，不再用會讓版面跳動的文字。量測後：圖片拉角約 80 毫秒、換色與打字約 20 毫秒。
- **教訓**：互動中的「等待」要拆成兩件事：看得到變化的時間與算準的時間；前者用舊結果的快速近似（變形）頂著，後者在背景補上，而且絕不要用固定的等待來省計算。
- **來源**：2026-10-19 使用者回報；`web/src/lib/scheduler.ts`、`web/src/lib/geometry.ts`（`layerMap`）、`crates/stitch-compose`（`ItemLayer`）、`web/src/components/EditorCanvas.svelte`。

### 固定在畫面上的區域，裡面不能有時有時無的東西

- **理論說**：警告與提示放在畫布下面最顯眼；它們只是幾行字，出現或消失不會有什麼影響。
- **實際發生**：畫布是固定在畫面上方的，警告出現（「放不進框」）、消失、或出現「已經接著上次做到的地方」時，畫布卡片的高度跟著變，下面的工具整個跳動；使用者一邊改一邊看到版面抖動。深入量才發現還有一個隱藏原因：卡片裡 `:first-child` 的上邊界會穿出容器，讓有字與沒字的狀態差 12 像素。
- **解決方式**：固定區域只放高度固定的東西——畫布、一行狀態字（`flow-root` 並給最小高度）、角落的短提醒（不佔版面）；詳細警告、提示、接著做的說明都移到會捲動的工具區。用端對端測試量警告出現、消失前後的卡片高度。
- **教訓**：會因為內容而出現或消失的訊息，不能放在版面的固定區域裡；固定區域的高度要能被測試量到而且不變。
- **來源**：2026-10-19 使用者回報警告影響排版；`web/src/routes/EditorPage.svelte`、`web/tests/e2e/editor-flow.spec.ts`（警告不會讓畫布版面跳動）。
