# Phase 0 研究：技術決策

所有計畫中的未知項皆已解決，沒有遺留的 NEEDS CLARIFICATION。

## R1. 針法：v1 只用「填充＋輪廓」，不做緞面繡

- **決策**：文字與圖片色塊一律用填充針（掃描線，tatami）加一圈輪廓走針與底針；緞面繡延後。
- **理由**：緞面繡需要抽出筆畫中軸線，對繁體中文複雜字形很難，風險高。填充針只需多邊形加掃描線，
  可全自動、可用 golden 測試。符合 YAGNI 與「先讓媽媽用起來」。
- **代價**：細長筆畫的外觀不如緞面繡光滑。以「最小筆畫寬度」偵測補償（見 R6）。
- **考慮過的替代**：骨架化加緞面繡（工程量大、延後）；直接移植 Ink/Stitch（授權尚未決定，憲章未選 GPL，不採）。

## R2. 字形來源與字型

- **決策**：用 `ttf-parser` 讀字形輪廓，`kurbo` 把曲線展平成折線；字型內嵌於 PWA 並**子集化**到
  常用繁體字（約 4,800 常用字加英數與常見標點）。候選字型（皆為開源授權，實作前須逐一確認授權文字）：
  Noto Sans TC（黑體）、Noto Serif TC（宋體）、粉圓體 jf-openhuninn、霞鶩文楷 TC。
- **理由**：完整 CJK 字型 5～15MB 太大，離線快取與手機載入都吃力；子集化可降到數 MB 以內。
  輸入到不在子集內的字時，退回其他字型或提示（對應規格邊界情況）。
- **待辦（實作時）**：確認每個字型的授權條款允許嵌入、子集化與散布；授權檔放入 `fonts/`。
- **考慮過的替代**：執行時載入完整字型（太大）；用瀏覽器 Canvas 取字形（不可重現、難測試）。

## R3. 多邊形運算

- **決策**：`i_overlay` 做布林與偏移（輪廓內縮、底針範圍）；掃描線求交自行實作於 `stitch-geom`。
- **理由**：MIT/Apache、純 Rust、可編成 WASM；自行實作掃描線能完全控制針距與行偏移，並容易寫 golden 測試。
- **考慮過的替代**：`geo`（較重）；Clipper2 綁定（需 C++ 工具鏈，WASM 麻煩）。

## R4. 圖片轉色塊

- **決策**：前端用瀏覽器解碼圖片成 RGBA 位元組交給 Rust；Rust 以 `visioncortex` 做色彩分群與輪廓追蹤，
  再交給 `stitch-geom` 簡化，過小區塊合併或丟棄。
- **理由**：避免在 WASM 內放大型圖片解碼器；`visioncortex` 已知可編成 WASM，授權寬鬆。
- **限制**：v1 只保證色塊明確的圖案；照片給提示但不保證品質（規格 User Story 4）。

## R5. 輸出格式與檔名

- **決策**：`stitch-formats` 提供「格式註冊表」（`trait Format` 加註冊清單），v1 註冊 DST 與 EXP；
  新增格式只需新增一個實作並註冊，不影響既有程式與設定。
- **DST**：512 位元組表頭（標籤、針數、範圍），針跡為三位元組平衡三進位編碼，單針位移上限 ±121（0.1mm 單位），
  超過需拆分；Y 軸方向與畫面相反。**EXP**：兩位元組位移，`0x80` 開頭為控制碼（跳針、換色），單針位移上限約 ±127。
  具體位元佈局將以 pyembroidery 的行為作為交叉驗證對象，並用 golden 位元組測試鎖定。
- **檔名**：機器對檔名常有限制，中文檔名風險高。決策：主檔名使用 ASCII 的 `A-Z0-9`、最長 8 字元，
  例如 `WANG0001.DST`；中文名稱只顯示在畫面上，並在畫面列出「畫面名稱 ⇄ 檔名」對照。
  詳見 [contracts/output-files.md](./contracts/output-files.md)。
- **理由**：B70 檔案命名限制未知，以最保守規則處理，降低「機器讀不到」的風險。

## R6. 最小可繡尺寸

- **決策**：預設下限——字高 ≥ 4mm（可繡），筆畫寬 ≥ 0.8mm；低於下限先自動放大，放大後超出框則阻止並建議換大框。
  數值放在可調整的設定中，由媽媽實測回饋後校正。
- **理由**：沒有實機資料，採常見經驗值並可調整。這些數字是**假設**，需實測驗證（見 R9）。

## R7. 繡框安全範圍

- **決策**：每個框有「可繡寬高」與「安全邊距」（預設 5mm）；設計必須完全落在「可繡區 − 安全邊距」內。
  圓形與橢圓以幾何方程式判斷，方形以矩形判斷。輸出前由核心驗證，前端不得繞過。
- **理由**：憲章原則四與規格 FR-008、FR-009、SC-004：超出範圍的檔案絕不輸出。
- **內建框**：大 1600×2600、中 1200×1800、小 500×750（單位 0.1mm），來源為零售商公開資訊，使用者可檢視。

## R8. 前端與 PWA

- **決策**：Svelte 5 加 Vite；`vite-plugin-pwa` 產生 service worker 預快取 WASM、字型與靜態資源；
  預覽用 Canvas 2D 畫針跡（每針畫一小段線，帶方向與微光澤）。
- **理由**：Svelte 輸出小、適合手機；v1 針數數萬針，Canvas 2D 足夠，不必上 WebGL（YAGNI）。
- **考慮過的替代**：React（較大）；WebGL 預覽（延後，除非 Canvas 效能不足）。

## R9. 傳到 USB 的方式（需實機驗證的假設）

- **決策**：以「下載多個檔案」為主，並提供「分享」按鈕（Web Share API 傳檔案）作為備援，讓媽媽選擇
  「檔案」App 再存到插上的 USB。核心不假設能直接寫入 USB。
- **理由**：Android Chrome 對目錄選取（`showDirectoryPicker`）支援不確定，不依賴它。
  媽媽手機實際行為（下載資料夾位置、能否存到 OTG）**必須實機確認**，列入給媽媽的測試清單。
- **風險**：一次下載多個檔案，Chrome 可能詢問是否允許；說明文字要提醒按「允許」。

## R10. 沒有實機時的驗證替代

- **決策**：以 pyembroidery 讀回我們輸出的 DST 與 EXP，比對針數、座標、換色；並以數個已知小型圖樣做 golden 位元組測試。
  此驗證只證明「檔案格式正確」，**不證明 B70 能讀**；B70 實機結果仍是 SC-006 的唯一驗收。
- **理由**：有獨立實作交叉驗證，能大幅降低格式本身寫錯的風險，剩下的只是機器相容性問題。

## R11. 測試策略（對應憲章 TDD）

- 核心：單元測試加 golden（針跡序列）加往返（寫→讀）加屬性測試（任意輸入下不超出範圍、單針位移不超限）。
- 前端：vitest 測互動邏輯；Playwright 以手機視窗跑主要流程（輸入文字→選框→輸出）。
- 任務順序：每個實作任務前面必有先失敗的測試任務。
